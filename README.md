# 有梗接歌檢索 · Gag-Retrieval

給定正在播放的一首華語歌，從歌詞語料庫中找出**「歌詞語意上有梗、且直觀」**的
下一首歌以及要接進去的**那一句**——像現場 DJ 那樣，讓觀眾一聽就 get 到接點。

這是一個 **AI DJ 串燒系統的「選歌 / 選 cue point」層**：它不負責把兩首歌混音，
而是回答「下一首該接誰、從哪一句接、為什麼有梗」，把帶著完整證據的選項交給
下游的接歌 agent。

---

## 我們要的「梗」長什麼樣

理想範例（都是華語圈耳熟能詳的接法）：

| 上一首（A） | 下一首（B）接進來的那一句 | 梗的類型 |
|---|---|---|
| 我要飛（副歌反覆「飛」「我要用力飛」） | 熱狗《飛太遠》「**飛太遠** 衝上雲端」 | 主題語意對主題語意 |
| 蔡依林《說愛你》「這一刻我終於勇敢**說愛你**」 | 王心凌《**愛你**》招牌副歌 | 頂真＋歌名梗 |
| 陶喆《今天你要嫁給我》 | 「明天我要嫁給你」 | 同句反轉 |

它們有三個共同特徵，就是本專案的設計核心：

1. **對應的是被「轟炸過的語意」，不是碰巧相同的字。**《我要飛》整首把「飛」織進
   九個不同句子，觀眾整首歌泡在「飛」的語意裡，所以《飛太遠》一進來就 get；反之
   「快樂」只出現在某首歌的一句歌詞（就算 loop 三次）就不是那首歌的語意，拿它接歌
   沒人會反應（**同字不同意＝假梗**）。
2. **B 進來的必須是「一聽就認得」的招牌句**（歌名句 > 副歌 > 首句）——冷門歌的第 37
   句字面再工整也沒人笑。
3. **呼應要在 B 進歌的第一秒發生**——埋在 B 句尾的呼應會遲到八個字，梗就涼了。

## 兩階段架構

```
                    給定正在播放的歌 A ＋ 歌詞語料庫（N 可無限大）
                                     │
     ┌───────────────────────────────▼─────────────────────────────────┐
     │  Stage 1 · 檢索（零 LLM，與 N 無關的索引查詢，可規模化）           │
     │   字元 bigram 倒排索引 ＋ 句首字接龍索引                            │
     │   排序 = 錨點語意飽和度(spread) × B句辨識度 × 進歌時效 × 知名度      │
     │   → top-K 候選歌，每首附「證據句對」                                │
     └───────────────────────────────┬─────────────────────────────────┘
                                     │  只剩 5–10 首
     ┌───────────────────────────────▼─────────────────────────────────┐
     │  Stage 2 · LLM 裁判（Gemini / OpenAI 相容 / 本地 vLLM）            │
     │   拿到 A 與候選的完整歌詞 ＋ 各自「主題語意」清單 ＋ 接點線索        │
     │   判斷：同字不同意剔除、語意場延伸（飛↔翅膀/雲端）、選最直觀的一句    │
     │   → 下一首 ＋ A 出點句 ＋ B 進點句 ＋ 梗型 ＋ 理由 ＋ 信心           │
     └───────────────────────────────┬─────────────────────────────────┘
                                     ▼
                      交給下游接歌 agent（cue = 出點句尾 / 進點句首）
```

**為什麼是兩階段：** N 首歌的完整歌詞塞不進一次 LLM 呼叫，但字面/接龍索引可以把
範圍瞬間縮到 5–10 首（查詢成本與 N 無關，規模化時把 dict 換成 Elasticsearch 即可）。
Stage 1 只做召回＋粗排（把「可能有梗的」都撈進來，不做最終品味判斷），Stage 2
才做「哪個最直觀、字面像但其實沒梗要剔除、語意延伸的隱藏好梗」這種只有 LLM 做得到
的判斷。

**為什麼 LLM 只當裁判不當諧星：** 候選已被字面規則篩到「都有明確接點」，LLM 的工作
是**驗證 / 改選 / 剔除**已找到的對應（判別比生成容易得多），而不是自由發想笑點——
prompt 刻意不給檢索分數、要求它讀完整歌詞自行重判、內建正負例校準 confidence。

## Stage 1 的訊號（都從 LRC 結構自動算，零標注）

| 訊號 | 意義 | 怎麼算 |
|---|---|---|
| **語意飽和度 spread** | 錨點詞織進 A 幾個**不同**句子＝它是不是這首歌的「意思」 | 含該詞的相異句數（≥2 才算主題；單句 loop 不算） |
| **錨點身分** | 這個詞是不是某首歌的識別詞 | 歌名詞 1.0 > 主題詞 0.6 > 一般詞 0.3 |
| **B 句辨識度** | B 進來的句子觀眾認不認得 | 歌名句 > 副歌(重複句) > 首句 > 一般句 |
| **進歌時效** | 呼應是否落在 B 進歌第一秒 | 錨點在 B 句首 ≫ 埋在句尾 |
| **頂真接龍** | B 首字接住 A 尾詞（…說愛你→愛就是…） | 專屬句首字索引（這種句對沒有共同 bigram） |

**只排序、不排除**：高頻詞（如「愛你」）是合法的梗（它是《愛你》的歌名）；被硬性
排除的只有純虛詞/語法架構詞（「的看」「這一刻」「今天」「給我」這類時間/語法/代詞
組合）——判準是錨點必須是語意重心而非框架詞。

Stage 2 拿到的不只是候選，還有每首歌的**主題語意清單**（`theme_profile`：被反覆
轟炸、留在觀眾耳中的詞），這讓它能做字面檢索做不到的**語意場**匹配——A 轟炸「飛」，
B 用「翅膀」「衝上雲端」回應也算數。

## 安裝與執行

**零第三方依賴**（純 Python 標準函式庫），用系統 `python3` 直接跑即可。

```bash
git clone <this-repo>
cd gag-retrieval

# 1) 命令列：Stage 1 檢索 + 產生 Stage 2 提示詞（不需要任何 API key）
python3 -m gag_retrieval.run --corpus lrc_test --query 我要飛

# 2) Stage 2 直接呼叫 LLM 裁判
export GEMINI_API_KEY=你的key          # 或放進 gag_retrieval/gemini.key（已 gitignore）
python3 -m gag_retrieval.run --corpus lrc_test --query 我要飛 --llm gemini

# 3) Demo 網頁（曲庫瀏覽、每句試聽、雙 deck 接歌試聽、即時裁判）
python3 -m gag_retrieval.server --corpus lrc_test --port 8010
#   → 開瀏覽器 http://127.0.0.1:8010

# 4) 黃金範例自我測試（21 項：四種梗型 + 語意飽和度 + 接龍 + 各種噪音排除）
python3 -m gag_retrieval.selftest
```

> **埠被佔用？** 先 `pkill -f gag_retrieval.server` 或改 `--port 8011`。

### 語料格式

一首歌一個 `.txt`（或 `.lrc`），**檔名 = 歌名**，每行 `[mm:ss.xx]歌詞`：

```
[00:34.97]這一刻我終於勇敢說愛你
[00:40.22]一開始我只顧著看你
```

作詞/作曲等 credit 行會自動略過；繁簡混用沒關係（內建繁→簡正規化，裝了
`opencc` 會自動改用它）。要在 Demo 裡試聽，把同名音檔（`.mp3/.m4a/.wav`）放進
同一資料夾即可（檔名亂沒關係，用歌名模糊配對）。

### Demo 網頁功能

- **曲庫**：選一首當「正在播放」。
- **RETRIEVE**：跑 Stage 1（選項卡：錨點、梗型、語意飽和度、A 出點句 / B 進點句
  含秒數、B 句辨識度、剩餘秒數、段落位置）＋ Stage 2（Gemini 裁判卡）。
- **每句試聽**：句子旁的 ▶ 直接從那一秒播放。
- **試聽接歌**：雙 deck Web Audio crossfade——A 唱到出點句、等功率淡出，B 從進點句
  淡入，實際聽到接起來的效果。
- **串燒**：任何候選都能「設為正在播放」一路接下去（自動排除已播）。
- **音檔校準**：YouTube rip 常有多餘前奏，用側欄「校準」逐首對齊時間偏移（存
  `offsets.json`，套用到所有播放與試聽）。

## 作為 AI DJ 大系統的一個 Tool

`gag_retrieval/tool.py` 把同一個引擎包成兩個給 agent 呼叫的函數，對應兩個決策層：

```python
from gag_retrieval.tool import GagCatalog
cat = GagCatalog("lrc_test")               # 載入一次

# Tool 1 — 選歌層（在 orchestrator / 串燒主迴圈，接歌 agent 之外）
cat.suggest_next_song("我要飛", k=5, exclude={"已播過的歌"})

# Tool 2 — 選 cue 層（歌對已定，注入接歌 agent 的 seed / 當 inspect 工具）
cat.lyric_hooks("我要飛", "飛太遠", k=5)
```

**怎麼變成「不可跳過的第一階段」而不是可有可無的工具：**

- **選歌層**天生不可跳過——接歌 agent 收到的是「已選定的兩首歌」，選歌發生在它
  之外的 orchestrator，`suggest_next_song` 就是那個 orchestrator 的必經步驟。
- **選 cue 層**要不可跳過，就把 `lyric_hooks` 的輸出**寫進接歌 agent 的 seed prompt**
  （prompt 裡的資料無法被跳過），或比照現有 agent「build 前必須先 inspect」的
  gating，把它註冊成一個必須先呼叫的 inspect 工具。

**關鍵設計原則：工具只附「誠實的 metadata」，不替 agent 過濾可行性。** 每個選項同時
帶「梗證據」（錨點、梗型、語意飽和度）和「客觀事實」（cue 秒數、B 剩餘 runway、段落
位置）。一個字面超有梗但 BPM 差 40、調性相剋的接法照樣回傳——因為那可能正是生成式
橋段（generate_bridge）能救、而且救回來最精彩的接法。**梗分數 × 聲學可行性的綜合
判斷留給 agent 的耳朵，工具不越權。** 回傳的 `line_a.end` / `line_b.start` 就是下游
的 `a_out` / `b_in` cue。

## 模組

```
gag_retrieval/
  zhnorm.py     文字正規化（NFKC / 繁→簡 / 標點 / 英文詞界）
  lrc.py        LRC 解析 → 句組（重複次數 = 副歌訊號）
  hooks.py      錨點身分、語意飽和度 spread、theme_profile 主題語意
  lexical.py    bigram 倒排索引 ＋ 句首字接龍索引 ＋ 錨點抽取
  meta.py       句子位置學（line_end / 段落 / runway / pos_pct）
  retrieve.py   Stage 1 編排（句對評分 → 聚合成歌 → top-K）
  judge.py      Stage 2 提示詞 ＋ LLM 後端（Gemini / OpenAI 相容 / vLLM，純 urllib）
  tool.py       給 agent 的兩個函數（suggest_next_song / lyric_hooks）
  server.py     Demo 網頁後端（純 http.server，含音檔 Range 串流）
  demo.html     單檔前端（白底、雙 deck 試聽、校準）
  align.py      時間戳精修骨架（官方歌詞 × Whisper 時鐘字元對齊，尚未接入）
  run.py        命令列
  selftest.py   黃金範例測試
```

### 選配：時間戳精修（align.py）

LRC 行級時間戳不準時，用 **Whisper 的時鐘、官方歌詞的字**：Demucs 分離人聲 →
Whisper 跑出它自己的詞級時間（字可以錯）→ 把 Whisper 字流與官方歌詞做字元對齊，
官方歌詞繼承精確時間。ASR 把「嫁給我」聽成「駕給我」也沒關係——位置對上，時間就
轉移過去，歌詞文本保持官方版。（骨架已完成，尚未接入 Demo。）
